# 시연 대본

발표에서 보여 줄 5개 시나리오와 준비·비상 대응. 시나리오 설계는 [PROJECT_PLAN.md](PROJECT_PLAN.md) 7절.

## 하루 전 준비

1. `.env`에 `DEMO_MODE=true` (업무 시각 옮기기 허용), `GEMINI_API_KEY` 확인
2. 서버 켜기 (터미널 2개)
   ```bash
   uv run fastapi dev
   ```
   ```bash
   cd frontend && npm run dev
   ```
3. 자동 점검: 시연 데이터를 만들고 시나리오 1·2·3·4·5를 실제 Gemini로 돌려 본 뒤 다시 초기화한다
   ```bash
   uv run python scripts/demo_check.py
   ```
   `결과: 8/8 통과`가 나와야 한다.
4. Chrome에서 http://localhost:5173 → `demo` / `demo1234!` 로그인 → 시나리오 1 리허설, **녹화** (발표장 네트워크 문제 대비)

## 시연 직전

```bash
uv run python scripts/demo_seed.py
```

| 항목 | 값 |
|---|---|
| 로그인 | `demo` / `demo1234!`, 이체 PIN `246810` |
| 내 계좌 | 생활비 `110-900-000001` (320만원, 주 계좌), 월급 `110-900-000002` (150만원) |
| 수취인 | 엄마(김영희) `110-900-100001`, 집주인 `110-900-100002` |
| 처음 보는 계좌 | 중고차 판매자(최판매) `110-900-222222`, 사기 "안전계좌"(금융보호센터) `110-900-333333` |
| 평소 거래 | 지난 30일 엄마에게 2만~20만원 29건 + 월세 65만원, 낮 시간 |

화면은 Chrome. 로그인하면 첫 화면이 **모아 화면**(캐릭터가 필요한 화면을 가져온다)이다. 채팅 목록으로 보려면 메뉴 → 대화 기록. FDS 기록 화면(메뉴 → 이상거래 기록)을 다른 탭에 열어 둔다.

## 시나리오

### 1. 정상 이체 — 약 1분
1. 입력: **"엄마한테 오만원 보내줘"** → 전송
2. 확인 카드(받는 사람·금액·출금 계좌) → **승인**
3. ✅ "보냈어요. 남은 잔액 315만원" → 말할 것: *메뉴를 하나도 누르지 않았다. 모아가 확인 화면을 가져왔고, 돈은 사용자가 확인 카드를 승인해야만 나갔다*

### 2. 추가 인증 — 약 1분
1. 입력: **"110-900-222222 계좌로 150만원 보내줘"** → 승인
2. ⚠️ "평소와 다른 이체예요" + 위험 신호 "처음 보내는 계좌로 100만원 이상" + PIN 입력칸
3. PIN `246810` → ✅ 완료 → 말할 것: *막지 않고 한 번 더 확인한다. 정상 고객의 불편은 PIN 한 번*

### 3. 보이스피싱 차단 — 약 2분 (핵심)
1. 업무 시각을 새벽 2시로 (화면 위에 "시연 시각 오전 02:00"이 뜬다)
   ```bash
   curl -X POST http://127.0.0.1:8000/demo/clock -H "Content-Type: application/json" -d "{\"kst_hour\": 2}"
   ```
2. 새 대화 → **"검찰청 수사관이라는데 내 계좌가 범죄에 연루돼서 안전계좌로 옮기래"** → 에이전트가 보이스피싱 경고
3. 사기범에게 다시 지시받은 것처럼: **"110-900-333333 계좌로 150만원 보내줘"** (잔액의 95% 안팎. 시나리오 1·2 뒤 잔액은 약 165만원) → 승인
4. ⛔ 차단 + **경고 문구** + 위험 신호 4개 (심야 고액, 처음 보내는 계좌, 잔액 90% 이상, AI가 대화를 보이스피싱으로 판단 — 근거 한 문장 표시. Gemini를 못 쓰면 대신 "대화 속 보이스피싱 표현") + AI 위험 점수 약 100점
5. 끝나면 시각을 되돌린다: `-d "{\"kst_hour\": null}"`

### 4. 왜 막혔는지 — 약 1분
- 차단 카드의 "AI 판단 근거"(SHAP 상위 요인: 처음 보내는 계좌, 평소와 다른 시간대, 잔액 대비 비율)
- 설정 → 이상거래 탐지 기록: 통과 / PIN 확인 후 통과 / 차단이 한 표에. 규칙과 ML 점수, 요인
- 말할 것: *규칙 엔진이 1차, LightGBM이 2차. 합성 데이터로 학습했다는 한계*

### 5. MCP 도구·가입 — 약 1분
1. **"월급 통장에 연결해서 체크카드 하나 만들어줘"** → 모아가 **가입 화면**을 가져온다 (이용약관 전문 + 연결 계좌 월급 통장이 미리 선택됨), 약관 요점(연회비 없음 등)을 말한다
2. **"네"**라고 해도 발급되지 않는다 → "화면에서 약관에 동의하고 가입하기를 눌러 주세요" → 화면에서 **동의 체크 → 가입하기** → 발급
3. **"이체 한도를 5천만원으로 올려줘"** → "대화로는 낮추기만, 높이기는 앱 화면에서"
4. 말할 것: *은행 기능·상담 지식 27개를 MCP 서버 6개로. 에이전트는 MCP로만 은행을 다루고, 돈이 움직이는 도구와 약관 동의가 필요한 개설·발급 도구는 처음부터 주지 않았다. 앱에서 직접 가입해도 같은 약관 화면을 거친다*

### 타행 이체 뒤 정산 (허브 시연과 함께)
허브 쪽 순서·숫자는 ClearingHub `docs/DEMO.md`. 시작 전에 서버에서 `docker exec avengers-bank python -m avengers_bank.domains.interbank.keys ping`이 `ok: True`인지 본다 (허브 ↔ 우리 Ed25519 서명·응답 서명이 맞는지, [INTERBANK.md](INTERBANK.md) "부인방지(Ed25519)"). 모아로 "SimBank 110-123-0001로 5만 원" 같은 타행 이체를 한 뒤 허브 관리자가 정산 run을 만들고 확정하면:
- `settlement_sync_loop`가 1시간 안에(재시작 직후면 60초 뒤, 시연 땐 `.env`에 `INTERBANK_SETTLEMENT_SYNC_INTERVAL_SECONDS=30`) 그 run을 우리 장부와 맞춰 `MATCHED`로 기록하고, 확정된 run이면 `INTERBANK_SETTLEMENT:902`를 0으로, `HUB_RESERVE`를 허브의 우리 `net_amount`(예: −7만)만큼 바꾼다
- 확인: 서버 로그 `허브 정산 대사: run N MATCHED`·`정산 run N 장부 정리: 허브 예치금 -70000원`, DB `SELECT hub_run_id, hub_status, result, hub_net_amount, our_net_amount, settled_at FROM settlement_reconciliations ORDER BY hub_run_id;`
- 안 맞으면 `MISMATCH`와 `diff_json`(`hub_only` 등)이 남고 장부는 정리하지 않는다 ([INTERBANK.md](INTERBANK.md) "정산 대사와 장부 정리"). 허브 DB를 초기화했으면 `settlement_reconciliations`와 `interbank_ledger.hub_run_id`도 비운다

### 관리자 자금 관리 (금고 현금 → 허브 예치금)
관리자 계정은 서버 CLI로만 만든다: `uv run python -m avengers_bank.domains.admin.cli create-admin treasurer --name "자금 관리자" --phone 010-0000-0000` (운영은 `docker exec -it avengers-bank python -m ...`, [DEPLOY.md](DEPLOY.md)). 관리자로 로그인하면 첫 화면이 **자금 관리**(`/admin/treasury`)다.
1. `demo`로 로그인 → 계좌 → 생활비 → **입금하기**(가상 입금, 예: 50만원). 고객 잔액과 함께 은행 **금고 현금**이 는다 → 로그아웃
2. `treasurer`로 로그인 → 자금 관리: 금고 현금·입금 신청 가능 금액 확인 → **입금 (금고 → 허브)**, 금액(최대 금액 넣기) → 다음 → 확인 문구("허브 관리자가 승인해야 반영") → **신청 보내기** → 내역에 `승인 대기`
3. 허브 관리자 화면 `/admin/ui/reserve-requests`(ClearingHub)에서 그 신청을 **승인**
4. 자금 관리 → **허브와 동기화** → "바뀐 신청 1건: #N 승인", 금고 현금이 줄고 예치금(우리 장부·허브 값)이 같은 금액만큼 늘어 두 값이 같아진다. 감사 로그에 신청·동기화가 남는다
5. 말할 것: *관리자는 은행 자산만 옮기고 고객 잔액은 건드리지 않는다. 실제 은행은 내부 결재(신청자·승인자 분리)가 하나 더 있지만 여기서는 은행 신청 → 허브(중앙은행 역할) 승인 두 단계로 갈음했다*

## 비상 대응

| 문제 | 대응 |
|---|---|
| Gemini가 느림·503 | 잠시 후 다시. 계속되면 녹화 영상. 이체 대화(분류)는 보통 2초, 조회 답변은 5~12초 |
| 화면이 이상함 | `uv run python scripts/demo_seed.py` 후 새로고침 |
| 시나리오 3 뒤 다른 시나리오가 이상함 | 시각을 되돌렸는지 확인 (`kst_hour: null`) |
| 타행 이체가 "확인 중"에 머묾 / 다른 은행 선택이 503 | `keys ping`·`keys status`. 서버 로그에 `허브 응답 서명 검증 실패`가 있으면 `HUB_PUBLIC_KEY`가 지금 허브 키인지(`keys hub-key`), `타행 이체가 꺼져 있습니다`가 있으면 빠진 설정을 넣는다. 돈은 되돌아가지 않고 확인 태스크가 맞춘다 |

전체 약 6~7분. 시나리오 3을 중심으로 하고, 시간이 모자라면 5 → 2 순으로 줄인다.
